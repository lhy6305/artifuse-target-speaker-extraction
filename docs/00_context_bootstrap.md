# 上下文恢复入口与协作规范

## 读取顺序
每次开始新一轮工作，或历史上下文被清空时，按以下顺序读取：

1. 本文档 `docs/00_context_bootstrap.md`
2. `docs/01_project_overview_and_plan.md`
3. `docs/02_pitfalls_log.md`
4. `docs/05_task_branch_map.md`
5. `initial_design.md`
6. `initial_design_judg.md`

如果当前活跃文档仍不足以恢复更早背景，再按下面顺序补读：

1. `docs/archive/README.md`
2. 对应主题的归档索引：
   - `docs/archive/project_overview/README.md`
   - `docs/archive/pitfalls/README.md`
   - `docs/archive/task_branch_map/README.md`
3. 再进入对应分卷文件，而不是直接回到超长主文档里全量查找
4. 如果需要补实验推进时间线，再读：
   - `reports/daily/README.md`
   - 对应月份索引 `reports/daily/index_YYYY-MM.md`
   - 最后才进入具体日报

## 强制规范
### 1. 编码规范
- 全部代码、脚本、文档统一使用 UTF-8 无 BOM。
- 读取文本时必须显式指定 UTF-8；命令行读取优先使用支持显式编码的方式。
- 发现历史文件编码不一致时，先记录到踩坑文档，再转换为 UTF-8 无 BOM 后继续修改。

### 2. Python 环境
- 只能使用仓库根目录下的 `python.exe`。
- 禁止调用系统 Python，避免依赖缺失和环境漂移。
- 后续所有 Python 命令默认写成 `.\python.exe ...`。

### 3. 提权执行约束
- 涉及声音处理、Torch 训练、原生库调用、长时间推理、批量特征提取等业务代码时，必须使用沙盒提权运行。
- 普通只读检查、轻量文本处理、文档维护可先在沙盒内执行。
- 如果关键命令因沙盒限制失败，应立即改为提权重试，不绕过该要求。

### 4. 文档维护纪律
- 推进任何任务时，必须同步更新磁盘文档，不能只留在对话里。
- 文档至少持续覆盖以下内容：
  - 项目结构介绍
  - 总任务大纲
  - 当前任务进度
  - 当前阶段验收标准
  - 下一阶段任务
  - 开发踩坑点
- 旧文档若过时，必须修改说明或移入归档目录，禁止直接删除。
- 当主文档增长到明显不利于接班阅读时，应优先采用：
  - 活跃摘要留在 `docs/`
  - 历史记录拆分到 `docs/archive/`
  的方式整理，而不是继续把所有历史堆在单文件里。

### 5. 恢复与交接要求
- 应假设历史对话随时会丢失，所有关键判断、阶段结论、阻塞项都要落盘。
- 进入下一阶段前，先确认当前文档是否足以支持其他人接手。

### 6. 目录结构与临时文件管理
- 无论何时，都必须维护清晰的项目目录结构。
- 临时文件必须放在专门位置，并带有明显标记，例如 `tmp/`、`scratch/`、`*_tmp.*`。
- 临时文件在使用后必须判定去向：
  - 若仍有长期价值，迁移为正式文件并更新文档。
  - 若无价值，及时清理删除。
- 不允许长期把实验输出、草稿脚本、一次性结果混放在根目录。
- 必要时可自行建立 Git 仓库，但仍需保持目录和提交边界清晰。

### 6.1 Git 使用边界
- Git 由用户手动维护，助手不负责创建、修改或补做提交记录。
- Git 对助手的主要作用仅限于：
  - 检查当前改动边界；
  - 核对哪些文件被跟踪或忽略；
  - 在误操作时辅助定位和恢复。
- 更新文档或代码时，可以使用 `git status`、`git diff`、`git log` 做事实核对，但不要把“准备提交”或“已经提交”当作默认工作流的一部分写死。

### 6.2 `.gitignore` 与可恢复边界
- `.gitignore` 的默认目标不是“尽量多忽略”，而是同时满足：
  - 不泄露原始/敏感/重资产；
  - 在误删除或对话丢失时，尽量保住可恢复所需的小型结构化元数据。
- 不能因为目录里有大文件，就把整类恢复关键文件一起整体忽略。
- 默认应保持可跟踪的恢复元数据包括：
  - `experiments/**/train_summary.json`
  - `reports/eval/**/eval_summary.json`
  - `reports/eval/**/summary.json`
  - blind pack 的 `README.md`、`blind_key.json`、`sample_meta.json`
- 默认继续留在本地的内容包括：
  - 原始音频、版权受限音频、标注文本
  - synthetic 生成音频
  - checkpoint、张量权重、二进制运行产物
  - 指向本地/非公开资产路径的 manifest
- 任何一次调整 `.gitignore` 后，都要至少核对一次：
  - `git status --short --ignored`
  - 确认恢复关键摘要没有被误伤
  - 确认重资产仍留在 ignore 边界内

### 7. 方案决策流程
- 所有方案决策最终都交由用户判断。
- 在给出方案选项前，必须先完成必要的数据收集和事实核对。
- 汇报方案时，必须直接说明：
  - 当前观察到的数据事实
  - 可选方案
  - 每个方案的优点
  - 每个方案的缺点或风险
- 建议选择及其理由
- 未经用户确认，不把存在明显取舍的方案当作既定结论写死。

### 8. 训练执行纪律
- 跑训练时必须打印明确时间信息，至少包含开始时间、结束时间和耗时。
- 在任何大规模训练前，必须先完成小规模训练验证，确认命令、数据读取、日志落盘、checkpoint 和基础速度都正常。
- 禁止在小规模训练尚未跑通前，直接依据主观感觉或单次命令响应时间去估计硬件速度与完整训练耗时。

### 9. 网络使用纪律
- 除了助手内置的搜索能力外，工作区默认全部离线运行。
- 如需使用外部网络，例如：
  - 拉取项目依赖代码
  - 拉取预编译模型
  - 安装 `pip` 包
  - 下载数据或工具链
- 必须先停止当前自动推进，向用户简要说明原因，并直接给出建议命令。
- 这类操作不通过沙盒提权代替，也不由助手擅自联网执行；等待用户手动操作后再继续。

### 10. 沟通可理解性
- 在保持专业严谨技术术语的同时，额外补几句大白话解释当前在做什么。
- 特别是以下场景必须补充通俗说明：
  - 正在执行的步骤
  - 发现的问题
  - 需要用户决策的分歧点
  - 某个结果为什么重要
- 目标是让非实现细节视角下也能看懂“这一步到底在干什么、为什么要做”。

## 文档状态维护规则
- 每完成一个子任务，至少更新一次：
  - `docs/01_project_overview_and_plan.md` 的进度和下一步
  - `docs/02_pitfalls_log.md` 的新发现
- 若后续新增专题文档，需在 `docs/01_project_overview_and_plan.md` 中登记用途和入口。
